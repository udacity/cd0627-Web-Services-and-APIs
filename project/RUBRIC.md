# Project Rubric

The project rubric helps students understand what they need to do to meet specifications and helps reviewers evaluate submissions fairly. Each rubric consists of sections, which are groups of rubric items.

---

## Section 1: Resilience & API Design (Step 1)

| CRITERIA | MEETS SPECIFICATIONS | REVIEWER TIPS |
| :--- | :--- | :--- |
| **Circuit Breaker Implementation** | The student implements a REST endpoint (`POST /api/returns`) protected by a Resilience4j `@CircuitBreaker`. The circuit breaker points to a valid fallback method. | Check `RmaController.java` for the `@CircuitBreaker` annotation. Ensure the `name` attribute matches the configuration in `application.properties` (e.g., `"rmaService"`). |
| **Graceful Degradation** | The fallback method correctly catches exceptions and returns a structured response with an HTTP 503 (Service Unavailable) status. | The fallback method signature must match the original method but append a `Throwable` parameter at the end. Check that `ResponseEntity.status(HttpStatus.SERVICE_UNAVAILABLE)` is used rather than returning a 200 OK with an error message. |

## Section 2: Controller Slice Testing (Step 2)

| CRITERIA | MEETS SPECIFICATIONS | REVIEWER TIPS |
| :--- | :--- | :--- |
| **Controller Slice Testing** | The student implements unit tests verifying the denied path and the circuit breaker fallback behavior using MockMvc. | Check `RmaControllerTest.java`. Verify that Mockito mocks are set up correctly using `@Mock` and `@InjectMocks`. Ensure they mock the service behavior and assert the correct HTTP status codes (200 for normal and 503 for fallback) and JSON response contents. |

## Section 3: AI Integration (Step 3 & Step 4)

| CRITERIA | MEETS SPECIFICATIONS | REVIEWER TIPS |
| :--- | :--- | :--- |
| **Structured Output Parsing** | The student uses `BeanOutputConverter` to instruct the LLM to return JSON and parses it into a typed `ReturnAnalysis` record. | Check `RmaService.java` Step 3. The prompt string must explicitly include the format instructions generated by `converter.getFormat()`. Verify the LLM response is converted successfully. |
| **Vector Store Seeding** | The application safely reads `policy-seed.txt` and seeds the `SimpleVectorStore` at startup. It includes a guard to prevent startup crashes if the OpenAI API key is missing. | Check `AiConfig.java`. Look for an `@PostConstruct` method (or custom seeding logic inside the bean definition). If they don't check for the presence of `OPENAI_API_KEY` (or if it equals "mock-key"), they may experience startup failures during testing. |
| **Retrieval-Augmented Generation (RAG)** | The student uses `QuestionAnswerAdvisor` attached to a `ChatClient` call to ground the AI's decision in the return policy. | Check `RmaService.java` Step 4. Ensure `.advisors(policyAdvisor)` is chained onto the `ChatClient` request. If missing, the AI is making decisions without reading the policy document context. |

## Section 4: Event-Driven Architecture & CQRS (Step 5 & Step 6)

| CRITERIA | MEETS SPECIFICATIONS | REVIEWER TIPS |
| :--- | :--- | :--- |
| **Event Publishing (Command Side)** | The application publishes a `ReturnApprovedEvent` to the `returns-topic` using `KafkaTemplate` **only** when a return is approved. | Check `RmaService.java` Step 5. Ensure the `kafkaTemplate.send()` method is wrapped in a conditional block checking if the AI decision was approved. |
| **Event Consumption (Query Side)** | The application consumes events from the `returns-topic` and stores them in the `dashboardView` map. | Check `DashboardService.java` Step 6. Look for `@KafkaListener(topics = RETURNS_TOPIC, groupId = "dashboard-group")`. Verify the method accepts a `ReturnApprovedEvent` so Jackson deserialization happens automatically. |
| **GraphQL Query Mapping** | The student exposes the read model via a GraphQL query resolver matching the provided schema. | Check `DashboardController.java` Step 6. The method must be annotated with `@QueryMapping` and its name (`returnsDashboard`) must match the Query field defined in `schema.graphqls`. |

## Section 5: Asynchronous Integration Testing

| CRITERIA | MEETS SPECIFICATIONS | REVIEWER TIPS |
| :--- | :--- | :--- |
| **Asynchronous Integration Testing** | The student implements an integration test that verifies the Kafka producer-to-consumer flow using `Awaitility`. | Check `RmaServiceIntegrationTest.java`. A common mistake is using `Thread.sleep()`. They must use `await().atMost(...).until(...)` to poll the dashboard service to ensure the event was consumed asynchronously. |

# Stand Out Suggestions

| SUGGESTIONS TO MAKE YOUR PROJECT STAND OUT |
| :--- |
| **Include at least three optional ideas for students who want to go beyond the core requirements. Encourage creativity, personal investment, and professional polish.** |
| 1. **Extend the GraphQL Schema:** Add a `status` field to the GraphQL schema and the Java event record so the dashboard explicitly shows "APPROVED" or "PENDING" for each entry. |
| 2. **Database Persistence:** Replace the in-memory `dashboardView` map with a Spring Data JPA repository and an embedded H2 database to persist the dashboard state across application restarts. |
| 3. **Advanced RAG Logic:** Enhance the `policyQuestion` prompt to offer partial refunds based on sentiment analysis, or introduce a "human-in-the-loop" review queue status for ambiguous cases. |
