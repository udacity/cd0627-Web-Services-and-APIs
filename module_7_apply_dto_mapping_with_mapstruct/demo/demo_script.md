# Demo Walkthrough: Request/Response Handling and DTOs (Module 7)

**Focus:** The Data Leak Problem — From Exposed Entities to Clean DTOs with MapStruct
**Target Length:** 5 - 7 minutes
**Files:** `ProductController.java`, `ProductMapper.java`, `CreateProductRequest.java`, `ProductResponse.java`

---

## 0:00 – 1:00 | Introduction & The Problem

*(Screen showing `Product.java` open in the IDE)*

"Welcome back. In this demo, we are going to look at Data Transfer Objects — DTOs — and how MapStruct eliminates the manual mapping boilerplate.

"Here is our `Product` entity. It has three fields: `id`, `name`, and `price`. This is simple, but imagine a real Order entity with internal fields like `internalMargin` or `auditTimestamp`. If we return the raw entity directly from our API, every internal field leaks to the client.

"The solution is to create a separate class — a DTO — that defines exactly what the client sees. Let's see how."

## 1:00 – 2:30 | The Response DTO: Java Records

*(Switch tabs to `ProductResponse.java`)*

"Here is our response DTO: `ProductResponse`. It is defined as a Java record — which gives us an immutable data class with constructor, getters, `equals`, `hashCode`, and `toString` all generated by the compiler.

"Notice it has exactly three fields: `id`, `name`, and `price`. If our `Product` entity had sensitive internal fields, they would simply be absent from the record. The client never sees them.

*(Switch tabs to `CreateProductRequest.java`)*

"And here is our request DTO: `CreateProductRequest`. This defines what the client sends when creating a product. Notice the validation annotations — `@NotBlank` on the name, `@Positive` on the price. The record and Bean Validation work together beautifully. If the client sends a blank name or a negative price, Spring automatically rejects the request with a 400 error before our code even runs."

## 2:30 – 4:00 | MapStruct: Zero-Boilerplate Mapping

*(Switch tabs to `ProductMapper.java`)*

"Now, how do we convert between the entity and the DTOs? We could write the mapping by hand — `new ProductResponse(product.getId(), product.getName(), product.getPrice())`. But with ten or twenty fields, this becomes tedious and error-prone.

"This is where MapStruct comes in. Look at `ProductMapper`. It is a plain Java interface annotated with `@Mapper(componentModel = "spring")`. We declare two methods: `toResponse()` takes a `Product` and returns a `ProductResponse`. `toEntity()` takes a `CreateProductRequest` and returns a `Product`.

"We write zero implementation code. MapStruct reads the field names at compile time, matches them by name and type, and generates the implementation class for us. Because the `componentModel` is set to `"spring"`, the generated class is automatically a Spring bean — we can inject it into any controller."

## 4:00 – 5:30 | The Controller: Putting It Together

*(Switch tabs to `ProductController.java`)*

"Let's see how the controller uses all of this.

*(Highlight the `createProduct` method)*

"In the `POST /products` endpoint, the method accepts `@Valid @RequestBody CreateProductRequest`. The `@Valid` annotation triggers Bean Validation — blank names and negative prices are rejected before we even get here. Then we call `mapper.toEntity(request)` to convert the DTO into our internal entity.

*(Highlight the `getProduct` method)*

"In `GET /products/{id}`, we load the entity and return `mapper.toResponse(entity)`. The mapper copies only the fields that exist in `ProductResponse`. Any internal-only fields on the entity are automatically excluded.

*(🖥️ Terminal: `mvn spring-boot:run`)*

*(🖥️ Terminal: `curl -s http://localhost:8080/products/1 | jq`)*

"Let's test it. `GET /products/1` returns a clean JSON response with only `id`, `name`, and `price`. No internal data leaked."

## 5:30 – 6:00 | Outro & Summary

"To summarize: DTOs define the contract between your API and the client. Java records make them trivially easy to write. Bean Validation annotations enforce input rules declaratively. And MapStruct generates the mapping code at compile time, so there is zero runtime overhead and zero boilerplate to maintain.

"Thanks for watching, and I'll see you in the next module."
