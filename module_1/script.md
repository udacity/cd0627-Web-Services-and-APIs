| The most important distinction to grasp is between action-oriented and resource-oriented API design. In an action-oriented, or RPC-style, API, your endpoints look like function calls: `/createUser`, `/getOrderStatus`, `/deleteItem`. This feels natural because it mirrors how we write code. But at scale, it creates a real problem—every new business operation demands a new, unique endpoint, and you quickly end up with hundreds of URIs that are hard to document, version, and secure. REST takes a fundamentally different approach. The URI identifies a resource—a noun like `/users` or `/orders/123`. The action is expressed through the HTTP method: GET to read, POST to create, PUT to replace, PATCH to update, and DELETE to remove. This separation of "what" from "how" is what makes REST scalable as a design philosophy. | **Complex Visual:** Create a two-column layout. Left column header: "RPC Style." | REST is more than clean URLs. It is defined by architectural constraints that work together to make APIs reliable at scale. First, statelessness: every request from a client must contain all the information the server needs to process it. The server stores no session state between requests. This is what allows you to horizontally scale by adding more server instances behind a load balancer—any server can handle any request because none of them remember previous interactions. Second, a uniform interface: all resources are accessed through the same consistent set of HTTP methods we just discussed, making the API predictable. Third, cacheability: responses should explicitly indicate whether they can be cached, which dramatically reduces server load and network latency. These constraints are not academic theory—they are the engineering reason REST-based systems serve millions of users without buckling. | |
| Let us look more closely at HTTP methods, because using the right method is not just a naming convention—it has real consequences for your infrastructure. HTTP methods have two critical properties: safety and idempotency. A safe method does not modify server state—GET is safe. An idempotent method produces the same result whether you send the request once or ten times—GET, PUT, and DELETE are all idempotent. POST is neither safe nor idempotent. And PATCH is not guaranteed to be idempotent—whether it is depends on the specific implementation. That said, a mature engineering team will design their PATCH operations to be idempotent anyway, ensuring safe retries across unreliable networks. Along with choosing the right method, you should also be deliberate about your response status codes. Status codes fall into families: 2xx for success, 3xx for redirection, 4xx for client errors, and 5xx for server errors. Pairing the correct method with the correct status code is what makes an API self-documenting. Why does idempotency matter in practice? Picture a customer placing an order on a spotty mobile connection. Their phone sends a POST request, the server processes the order, but the response gets lost in a network timeout. The phone retries automatically. Without careful design, that customer just got charged twice. | Before you design any endpoint, build the habit of asking three questions. What is the resource? What HTTP method correctly describes this operation? And what happens if this request is sent twice? If you can answer those clearly, you are building an API that scales, integrates cleanly, and avoids the cascading failures that come from sloppy distributed design.
