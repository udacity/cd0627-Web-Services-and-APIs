| In a traditional application, when a customer cancels an order, you update the order's status column from "confirmed" to "cancelled" in the database. The previous state is gone. You know the order is cancelled, but you have lost the history: when was it confirmed? Was it modified before cancellation? Did the customer change the shipping address between confirmation and cancellation? Event sourcing preserves that entire history by flipping how you think about persistence. Instead of a traditional state store that overwrites the current row, you use an event store—an immutable, append-only log of every event that ever happened to the entity. The current state is not stored; it is derived by replaying those events in order. In this lesson, we are going to understand event sourcing, CQRS, and how they work together to solve problems that traditional CRUD persistence cannot. | |
| In an event-sourced system, the event log is the source of truth. When a customer places an order, the system does not insert a row into an orders table. Instead, it appends an `OrderPlaced` event to the log. When the customer updates the shipping address, it appends a `ShippingAddressChanged` event. When the customer cancels, it appends an `OrderCancelled` event. Each event is immutable—once written, it is never modified or deleted. To determine the current state of the order, you replay all its events in sequence: placed, address changed, cancelled. The entity that manages this replay is called an aggregate. The aggregate is the consistency boundary—it enforces business rules before accepting a new event. For example, the Order aggregate would reject a `CancelOrder` command if the order has already been shipped, because "shipped" and "cancelled" are mutually exclusive states. The command handler validates the business rule against the current state, and if valid, appends the new event to the log. | **Complex Visual:** Design a vertical timeline flowing downward, like a ledger or transaction history. | Event sourcing naturally pairs with CQRS—Command Query Responsibility Segregation. The core idea is straightforward: separate your write model from your read model. The write side handles commands—business operations that validate rules and append events to the log. The read side serves queries—optimized, denormalized views of the data built specifically for how consumers need to read it. These read models are called projections. A projection listens to events from the log—using Spring's `@EventListener` annotation to react to each event as it is published—and updates a separate, query-optimized data store. For example, an `OrderSummaryProjection` might maintain a flat table with columns for order ID, customer name, status, and total amount—precomputed and ready for instant retrieval. The write model and read model are eventually consistent—there is a brief delay between an event being appended and the projection being updated. This eventual consistency is the fundamental trade-off: you gain independent scaling and optimized read performance, but you accept a small window during which the read model may lag behind the write model. | **Complex Visual:** Design a split-panel diagram divided by a vertical line. | The Saga pattern addresses a challenge that arises naturally in event-sourced microservices: distributed transactions. In a monolith, placing an order that requires payment, inventory reservation, and shipping can happen in a single database transaction. In a microservices architecture, each of those operations lives in a different service with its own database—there is no single transaction boundary. A saga coordinates these steps as a sequence of events. The Order Service emits `OrderPlaced`. The Payment Service reacts, processes payment, and emits `PaymentCompleted`. The Inventory Service reacts, reserves stock, and emits `StockReserved`. If any step fails—say the payment is declined—the saga triggers compensating events to undo the previous steps: `InventoryReleaseRequested`, `OrderMarkedAsFailed`. This is not atomic in the traditional sense—there is no rollback. Instead, sagas guarantee eventual consistency through explicit compensation logic. The important takeaway is the happy-path flow and the concept of compensating events. The deep mechanics of saga orchestration—choosing between orchestration and choreography, implementing idempotent event handlers—are a separate, advanced topic. | |
| To summarize: event sourcing stores what happened as an immutable log of events, and derives current state by replaying that log. Aggregates enforce business rules before appending new events. CQRS separates the write model from the read model, using projections to build query-optimized views that are eventually consistent. And the saga pattern coordinates multi-service transactions through event chains with compensating actions for failures. These patterns introduce real complexity—event schema evolution, eventual consistency, and projection management all require careful engineering. In production, aggregates with long event histories use snapshots—periodic state captures that let the system replay only events after the snapshot, bounding rebuild cost. These patterns are not a default architecture. Apply them when you genuinely need a complete audit trail, when you need independent read and write scaling, or when your domain has complex, multi-step business workflows that span service boundaries.
