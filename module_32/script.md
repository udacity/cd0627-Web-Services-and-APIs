# Module 32: Understand API Documentation and Testing

## Video 1: OpenAPI Specification and the Layered Testing Pyramid

| You have built a REST API with proper endpoints, error handling, and DTOs. But without documentation, no one can use it—and without tests, you cannot prove it works. These two concerns are more connected than they appear. Your API's OpenAPI specification defines what the API should do. Your tests verify that it actually does it. If either one is missing, your API is incomplete. In this lesson, we are going to understand the OpenAPI specification standard and the layered testing strategy that gives you both speed and confidence when verifying your Spring Boot APIs. | |
| The OpenAPI specification—currently at version 3.1—is a machine-readable description of your REST API. It documents every endpoint, every request parameter, every response schema, and every possible status code your API can return. API gateways can validate incoming requests against it. Code generators can produce client libraries from it. And testing frameworks can verify that your implementation matches the specification. In Spring Boot, you generate the OpenAPI specification automatically from your controller code using `springdoc-openapi`. This is the code-first approach—your code is the source of truth, and the spec is derived from it. The alternative is spec-first, where teams write the OpenAPI document before any code and generate server stubs from it. For Spring Boot APIs, code-first with springdoc is the pragmatic default. The library scans your `@RestController` classes, reads the annotations—`@GetMapping`, `@PostMapping`, `@RequestBody`, `@PathVariable`—and produces a complete OpenAPI document. It also serves an interactive Swagger UI at a configurable URL, where developers can explore and test endpoints directly from their browser. You can enrich the generated documentation using annotations like `@Operation` for endpoint descriptions and `@Schema` for field-level metadata—but the baseline specification is generated with zero manual effort. | |
| Testing a Spring Boot API effectively requires a layered approach. Each layer tests at a different level of isolation, and together they form a pyramid—many fast, narrow tests at the base, fewer comprehensive tests at the top. The base of the pyramid is the unit test. Unit tests verify a single class in complete isolation—no Spring context, no network, no database. You instantiate your controller or service directly in a JUnit test, mock all dependencies using Mockito, and verify that the logic produces the expected outputs for given inputs. Unit tests are extremely fast—they run in milliseconds—and they catch logic errors early. But they cannot verify that Spring wires your components correctly, that your JSON serialization works, or that your validation annotations fire. | The middle layer—and the most valuable for REST API testing—is the slice test, using `@WebMvcTest`. A slice test boots only the web layer of your Spring application—the controller, its JSON serialization, its validation, and its security configuration. It does not start the database, the service layer, or any infrastructure beans. You use `MockMvc` to send simulated HTTP requests to your controller and verify the response: the status code, the response body, the headers, and the content type. Dependencies like service beans are replaced with mocks. This gives you the ability to test your API contract—the exact shape of your REST responses—at a fraction of the cost of booting the full application. Slice tests verify what unit tests cannot: that `@Valid` rejects invalid input, that Jackson serializes your DTOs correctly, and that your error handler returns properly formatted Problem Details responses. If you are writing only one type of test for your REST controllers, make it a `@WebMvcTest`. For reactive WebFlux controllers, the equivalent tool is `WebTestClient`. | |
| The top layer is the full integration test, using `@SpringBootTest`. This annotation boots the entire Spring application context—controllers, services, repositories, security filters, and the embedded database. You send real HTTP requests to a server running on a random port and verify end-to-end behavior. Integration tests are the most comprehensive: they prove that every component is wired correctly and that the full request-response cycle works as expected. But they are also the slowest—booting the full context takes seconds, not milliseconds. Use integration tests sparingly and strategically: to verify critical user flows, to confirm that database queries return the expected data, and to ensure that your OpenAPI documentation endpoint is actually serving the correct specification at runtime. Do not fall into common testing anti-patterns: duplicating every unit test as an integration test wastes time without adding confidence, and testing implementation details—like verifying exact method call counts—instead of observable behavior makes tests break with every refactor. The goal of the layered pyramid is proportionality: many fast unit tests, a focused set of slice tests for your API contracts, and a small number of integration tests for end-to-end verification.
