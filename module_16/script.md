# Module 16: Understand API Gateway and Service Discovery

## Video 1: Why Microservices Need a Gateway and a Registry

| Once you decompose your application into microservices, every client request that used to hit a single application now needs to find the right service among many. The Order Service might be running on port 8081 today, on port 8083 tomorrow, and across three instances behind a load balancer next week. If your frontend hardcodes those addresses, every infrastructure change breaks the client. You need two things: a single entry point that shields clients from the internal service topology, and a mechanism that lets services find each other dynamically without hardcoded addresses. In this lesson, we are going to build a clear mental model for both—the API gateway and the service registry. | |
| An API gateway is a reverse proxy that sits between your clients and your internal microservices. Every external request enters through the gateway, and the gateway routes it to the correct backend service based on the request path, headers, or other attributes. This architecture provides three critical benefits. First, a single entry point—clients call one URL, not dozens of individual service addresses, which dramatically simplifies client-side logic. Second, cross-cutting concerns like authentication, rate limiting, and request logging can be applied in one place rather than duplicated across every service. Third, the gateway decouples your internal service topology from your public API surface—you can reorganize, scale, or replace backend services without any client-facing changes. Gateways can also handle protocol translation—converting between communication protocols like REST and gRPC—and response aggregation—combining results from multiple backend services into a single client response. Spring Cloud Gateway is the standard gateway implementation in the Spring ecosystem. It is built on Spring WebFlux, making it inherently non-blocking and designed for high-throughput traffic routing. You define routes declaratively, each consisting of a predicate—the condition a request must match, typically a URL path pattern—and a set of filters that modify the request or response as it passes through. | **Complex Visual:** Design a diagram with a phone and a laptop icon on the left side, both sending arrows toward a single large rectangular box in the center labeled "API Gateway (Spring Cloud Gateway)." | Now, how does the gateway know where the Order Service is actually running? That is the problem service discovery solves. A service registry is a centralized lookup table where every microservice instance registers itself when it starts up, providing its network address and port. When the gateway—or any service—needs to call the Order Service, it queries the registry instead of relying on hardcoded addresses. If the Order Service is running three instances across different ports, the registry knows about all three. Eureka, developed by Netflix and integrated into Spring Cloud, is the service registry used in this course. When a Spring Boot service includes the Eureka client dependency on its classpath, it automatically registers itself with the Eureka server at startup—no annotation required. Each service sends regular heartbeat signals to the registry. If the heartbeats stop—because the instance crashed or was shut down—Eureka removes that instance from the registry. This means the registry always reflects the current, live state of your infrastructure. When Spring Cloud Gateway is configured with Eureka, it resolves service names to actual network addresses automatically. In your route configuration, you reference services by their logical name—like `order-service`—rather than a physical URL, and the gateway uses the registry to locate the correct instance at request time. | **Complex Visual:** Design a three-layer diagram. | Client-side load balancing is the final piece of this architecture. There are two discovery patterns: in server-side discovery, the client sends requests to a central load balancer that queries the registry on its behalf. In client-side discovery—the model Spring Cloud uses—the caller queries the registry directly and makes the routing decision itself. When the gateway—or any service—resolves a service name through Eureka and gets back multiple instances, Spring Cloud LoadBalancer selects one of those instances using a strategy like round-robin. The caller makes the routing decision, not a centralized intermediary. To use this, you annotate your `WebClient` or `RestTemplate` bean with `@LoadBalanced`, and Spring intercepts outgoing requests to translate logical service names into actual addresses. This eliminates the need for a separate load-balancing infrastructure layer and keeps routing decisions close to the code that needs them. | |
| To summarize: the API gateway gives your clients a single, stable entry point and handles cross-cutting concerns centrally. The service registry gives your services the ability to find each other dynamically as instances come and go. And client-side load balancing distributes traffic across multiple instances directly from the caller, without a centralized load balancer. Together, these three mechanisms form the networking backbone of any production microservices deployment. One practical note: the revised scope for this course focuses exclusively on Spring Cloud Gateway and Eureka. In production, you may encounter alternatives like Consul or Kubernetes-native service discovery—the concepts are identical, only the tooling differs.
