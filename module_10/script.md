# Module 10: Understand Reactive Programming with Spring WebFlux

## Video 1: The Concurrency Problem — Thread-per-Request vs. Event Loop

| Script (one row per slide) | Guidance for Complex Visuals |
| :--- | :--- |
| As your API starts handling more users, more requests, and more downstream service calls, you will eventually hit a concurrency wall. How your application handles thousands of simultaneous connections—without crashing, without exhausting resources—is one of the most important architectural decisions you will make. In this video, we are going to understand two fundamentally different concurrency models: the traditional thread-per-request approach and the reactive event loop. Getting a clear mental model of both is essential before you can make a well-reasoned choice between them. | |
| For decades, Java web servers have operated on a thread-per-request model. When an HTTP request arrives, the server assigns it a dedicated operating system thread. That thread handles the request from start to finish—executing your controller logic, calling the database, waiting for the response, and sending the result back to the client. The critical problem is what happens during the "waiting" part. When your code calls a database or a remote service, the assigned thread blocks—it sits completely idle, consuming memory, doing nothing, until the I/O operation completes. Operating system threads are heavyweight resources. Each one consumes roughly one megabyte of stack memory. A typical server might maintain a pool of 200 threads. If all 200 are blocked waiting on slow database queries or downstream service calls, every new incoming request gets rejected. That is thread exhaustion, and it is one of the most common causes of production outages in synchronous Java applications. | **Complex Visual:** Design a visual showing a container labeled "Thread Pool" with five tall vertical bars inside, each representing one thread. On the left side, small arrow icons representing incoming requests enter and each "fills" one bar with color, indicating the thread is active. When a bar is waiting on I/O, show a small clock or hourglass icon next to it and change the bar's color to amber or orange—but it remains occupied and cannot accept new work. Progressively fill all five bars with amber. Then show new incoming request arrows bouncing off the container with a red "X" icon. Add a label at the bottom: "Thread Exhaustion — all threads blocked, new requests rejected." Keep the design simple with clean shapes and icons, no code. |
| The Reactive model, used by Spring WebFlux, takes a fundamentally different approach. Instead of assigning a thread per request, a small fixed number of event loop threads handle all incoming requests. When a request needs to perform I/O—a database call, an HTTP request to another service—the thread does not block and wait. Instead, it registers the I/O operation with the underlying system, notes where the processing should resume when the result arrives, and immediately moves on to handle the next incoming request. When the I/O result comes back asynchronously, a thread picks up where the work left off and completes the response. This is the model Spring WebFlux uses, built on top of Project Reactor. Because no thread ever sits idle waiting, a WebFlux application can handle tens of thousands of concurrent connections using just a handful of threads—a dramatic difference in resource efficiency compared to the thread-per-request model. | **Complex Visual:** Design a contrasting visual to the previous slide. Show a circular loop icon labeled "Event Loop" with one or two small thread icons orbiting inside it. On the left, incoming request arrows enter the loop. When a request needs I/O, a small arrow exits the loop toward a database or service icon on the right, and the request is placed in a small "waiting" area off to the side. The key detail: the loop thread immediately picks up the next incoming request—it never turns amber, it never stops. When I/O results return as arrows from the right, the request re-enters the loop for completion. The visual contrast with the previous slide should be clear: the thread is always in motion, always processing, and no requests are rejected. Note for designers: think of the event loop like a circular conveyor belt or a rotating carousel. The thread icons are small worker figures riding on the belt. Requests hop on and off the belt as they enter and leave. The belt never stops spinning. |
| WebFlux expresses this asynchronous model through two core types from Project Reactor: Mono and Flux. A Mono represents a single asynchronous value—think of it as a promise that will eventually produce zero or one result. A Flux represents a stream of zero to many asynchronous values, delivered over time. Every endpoint in a WebFlux application returns a Mono or a Flux instead of a plain Java object. This is what allows the framework to manage execution non-blockingly—your controller does not return data directly, it returns a description of how to produce the data, and the event loop schedules the actual work. One distinction that catches many developers off guard is the difference between cold and hot publishers. A cold publisher generates its data fresh for each subscriber—like opening a new database connection per request. A hot publisher broadcasts data continuously regardless of whether anyone is listening—like a live stock-price feed. If your code subscribes to a hot publisher late, the events that already fired are gone. Misunderstanding this distinction is one of the most common sources of data-loss bugs in reactive systems. Understanding this shift from "return a value" to "return a pipeline that produces a value"—and knowing whether that pipeline is cold or hot—is the conceptual foundation of reactive programming. | |
| To recap: the thread-per-request model is simple to reason about but wastes resources when threads block on I/O, and it breaks down under high concurrency. The event loop model, used by WebFlux, avoids this by never letting a thread sit idle—but it requires you to think in terms of Mono and Flux rather than traditional return values. In the next video, we will look at backpressure, the hidden complexity costs of reactive code, and how Java's Virtual Threads are changing this trade-off in a major way. | |

## Video 2: Backpressure, Virtual Threads, and Choosing the Right Model

| Script (one row per slide) | Guidance for Complex Visuals |
| :--- | :--- |
| In the previous video, we saw how the reactive event loop avoids thread exhaustion by never letting a thread block on I/O. But there is another concurrency problem that the reactive model solves which is just as important: what happens when data arrives faster than your application can process it. That problem is what backpressure addresses, and understanding it is key to understanding why reactive systems are resilient under load. | |
| Imagine a database query that returns ten thousand rows. In a traditional blocking application, the code reads rows one by one in a loop—it processes at whatever pace it can. But in a reactive pipeline, the data producer—the database driver—could push all ten thousand rows into your pipeline at once. If your consumer—say, a transformation step that enriches each row—is slower than the producer, those unprocessed rows pile up in memory. Without any flow control, memory usage spikes until the application crashes. Backpressure solves this. It is a flow-control mechanism where the consumer signals to the producer exactly how much data it is ready to handle. In Project Reactor, this is built into the reactive streams protocol. The subscriber requests a specific number of items—say, 256 at a time—and the producer only sends that many. When the subscriber finishes processing and is ready for more, it requests the next batch. This demand-driven flow means the system self-regulates instead of blindly accumulating data, making reactive applications inherently resilient to sudden load spikes. | **Complex Visual:** Design a two-panel visual. Left panel, labeled "Without Backpressure": show a large funnel or pipe at the top (labeled "Database — 10,000 rows") pouring a flood of small square icons (representing data rows) downward into a smaller container at the bottom (labeled "Consumer"). The container overflows with squares spilling out, and a warning icon or red "crash" label appears. Right panel, labeled "With Backpressure": show the same funnel at the top, but now there is a valve or gate between the producer and consumer. The consumer sends a small speech bubble upward saying "Send me 256." Only a small, controlled batch of squares passes through the gate. The consumer container holds them comfortably. The key message: controlled flow vs. uncontrolled flood. |
| There is, however, a significant cost. Reactive programming has a notoriously steep learning curve. It fundamentally changes how you write code—sequential, step-by-step logic is replaced with declarative operator chains like `flatMap`, `zip`, and `onErrorResume`. Debugging becomes harder because stack traces in a reactive pipeline no longer map cleanly to your logical code flow. And reactive code is infectious: once one layer of your application is reactive, every layer it touches—database access, service calls, error handling—must also be non-blocking. If you accidentally introduce a blocking call on the event loop, you starve the very threads responsible for handling all of your traffic. This complexity is real, and it is the primary reason many teams regret adopting WebFlux for applications that did not truly need it. | |
| This is where the conversation shifts. Java 21 introduced Virtual Threads—lightweight threads managed entirely by the JVM rather than the operating system. Unlike OS threads, which each consume roughly a megabyte of stack memory, Virtual Threads are extremely cheap—you can create millions of them with negligible overhead. The breakthrough is what happens when a Virtual Thread blocks on I/O. Instead of the OS thread sitting idle, the JVM automatically unmounts the Virtual Thread from the underlying carrier OS thread and schedules another Virtual Thread in its place. The carrier thread never actually idles. This means the traditional thread-per-request model, running on Virtual Threads instead of OS threads, achieves comparable throughput to the reactive event loop for standard request-response workloads—but with the simplicity of regular, sequential, imperative code. There are edge cases—such as code that holds `synchronized` locks during I/O—where a Virtual Thread can temporarily pin to its carrier thread and reduce throughput, but this has been significantly improved in recent JDK releases and is rarely a concern for typical web applications. No operator chains, no backpressure wiring, no reactive-specific debugging tools. Your existing blocking code just scales. | **Complex Visual:** Design a three-column comparison. Column 1, labeled "OS Threads (Traditional)": show five tall bars, most in amber (blocked/idle), with a label "~200 threads, expensive." Column 2, labeled "Event Loop (WebFlux)": show one or two active circular loop icons with a label "Few threads, never idle, complex code." Column 3, labeled "Virtual Threads (Java 21+)": show many small, lightweight bars densely packed (suggesting millions), all in active/green color, with a label "Millions of threads, simple code." The visual should convey that Virtual Threads combine the scale of the event loop with the simplicity of the traditional model. Note for designers: Column 3 should show a very large number of tiny thin bars (at least 30-50 visible) packed tightly together, all colored green. The visual density itself communicates "many." Use a much smaller bar height compared to Column 1's five large bars. |
| So when should you choose WebFlux, and when should you use Spring MVC with Virtual Threads? If you are building streaming APIs that continuously push data to clients—real-time dashboards, server-sent event feeds—or if you are building an API gateway that manages tens of thousands of simultaneous long-lived connections, the reactive model and WebFlux remain the strongest choice. But for the vast majority of backend services—standard request-response APIs with database calls and downstream service integrations—Virtual Threads on Spring MVC give you excellent scalability with dramatically simpler, more debuggable code. The decision should be driven by your actual workload and concurrency requirements, not by hype. Thanks for watching, and I'll see you in the next video. | |
