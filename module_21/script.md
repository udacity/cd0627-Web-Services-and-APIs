# Module 21: Understand LangChain4j for Java

## Video 1: LangChain4j's Declarative AI Services vs Spring AI

| The Java ecosystem now has two mature frameworks for integrating language models into production applications: Spring AI and LangChain4j. Spring AI provides a fluent, builder-based API—the `ChatClient`—that follows the same patterns as Spring's `WebClient` or `RestTemplate`. LangChain4j takes a fundamentally different approach: instead of a fluent API you call imperatively, LangChain4j lets you define an AI interaction as a plain Java interface, and the framework generates the implementation at runtime. These are not competing tools—they represent two distinct design philosophies. Understanding both gives you the vocabulary to choose the right one for your team's architecture. In this lesson, we are going to understand LangChain4j's declarative model and how it compares to Spring AI's builder pattern. | |
| The core abstraction in LangChain4j is the `@AiService` interface. You define a standard Java interface, annotate it with `@AiService`, and declare methods with descriptive signatures. The method's return type defines the expected output structure. The prompt is specified using `@SystemMessage` and `@UserMessage` annotations directly on the method. At runtime, LangChain4j generates a proxy implementation that handles prompt construction, LLM invocation, and response parsing—all behind a clean method call. This design pattern should feel familiar—it is the same interface-driven philosophy behind Spring Data repositories and Spring Cloud's `@HttpExchange` declarative clients. You write the contract; the framework writes the implementation. The key advantage is that your business logic never touches prompt strings, HTTP calls, or JSON parsing. It calls a typed method and gets a typed result. | **Complex Visual:** Design a two-layer diagram. | Where LangChain4j and Spring AI diverge most is their architectural philosophy. Spring AI follows the Spring "portable service abstraction" pattern—it is deeply integrated into Spring Boot's auto-configuration, dependency injection, and Micrometer observability. Your AI code feels like the rest of your Spring application. LangChain4j takes a framework-agnostic approach—it works identically across Spring Boot, Quarkus, Micronaut, and plain Java. It treats AI integration as a standalone library concern, not a framework concern. This distinction matters for your architecture decisions. If your team is fully committed to the Spring ecosystem and values standardized configuration via `application.yml` and native Spring Boot metrics, Spring AI is the natural fit. If your team works across multiple Java frameworks, or if you prefer explicit builder patterns over auto-configuration, LangChain4j gives you maximum portability. Both frameworks support the same critical capabilities—structured output, tool calling, RAG, and conversation memory—so the decision is about architectural fit, not feature gaps. Both also support conversation memory—the ability to maintain context across multiple user turns. The most common strategy is window-based memory, such as `MessageWindowChatMemory`, which retains the last N messages. Alternatives include token-based memory, which stays within a token budget, and summarizing memory, which compresses older exchanges into a condensed summary. Both frameworks also support streaming responses via Server-Sent Events—instead of waiting for the complete response, the model sends tokens incrementally as they are generated, enabling real-time display in the user interface. | |
| Tool calling in LangChain4j follows the same declarative philosophy. You define tool methods annotated with `@Tool`, and LangChain4j registers them with the model automatically. When the LLM determines that a tool is relevant to the user's query, it invokes the tool, receives the result, and incorporates it into its response. This cycle—the model reasons about the query, acts by calling a tool, observes the result, and decides whether to continue or respond—is called the agent loop. It turns your `@AiService` from a static text generator into an agent that can interact with your application's live services—querying databases, checking inventory, or calling external APIs. Interestingly, Spring AI 2.0 also uses the `@Tool` annotation for declarative tool registration. The architectural difference is in where tools live relative to the AI service definition. In LangChain4j, tools are co-located directly within the `@AiService` interface, making the agent's full capabilities immediately visible from a single file. In Spring AI, tools are separate Spring-managed beans that you pass to the `ChatClient` via `.tools()`, which provides more flexibility for reuse across multiple AI interactions but distributes the agent's behavior across the codebase. Neither approach is objectively better—it is a trade-off between locality and flexibility. | |
| To summarize: Spring AI and LangChain4j are complementary approaches to the same problem. Spring AI is ecosystem-native—ideal when your application is built entirely on Spring Boot and you want AI to integrate seamlessly with your existing infrastructure. LangChain4j is ecosystem-agnostic—ideal when you need portability, prefer interface-driven design, or want your AI service contracts to be as explicit as your REST contracts. In production, many teams use both: Spring AI for infrastructure-level concerns like vector store integration and observability, and LangChain4j for defining clean, testable AI service interfaces. The skill is knowing which to reach for based on the problem at hand. Thanks for watching, and I'll see you in the next video. | |
