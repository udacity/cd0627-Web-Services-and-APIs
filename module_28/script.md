## Video 1: Event Brokers vs Event Logs — RabbitMQ and Kafka

| Up to this point, every communication pattern we have discussed has been synchronous—one service calls another and waits for the response. That model breaks down when you need to decouple services temporally. Consider an e-commerce checkout: after a customer places an order, the system needs to send a confirmation email, update inventory, trigger fraud detection, and initiate payment processing. If any of those downstream services is slow or temporarily unavailable, a synchronous chain makes the customer wait—or worse, the entire checkout fails. Asynchronous messaging solves this by letting the Order Service publish an event and move on. Downstream services process that event at their own pace, independently. In this lesson, we are going to understand the two dominant messaging models and when each one applies. | |
| The first model is the message broker, represented by RabbitMQ. A message broker is a smart router—it receives messages from producers, applies routing rules, and delivers them to the appropriate consumer queues. RabbitMQ supports two core patterns. In point-to-point messaging, a message is placed in a queue and consumed by exactly one consumer—like a task assignment system where each task is processed once. In publish-subscribe messaging, a message is published to an exchange, which uses a routing key—a label attached by the producer—to determine which queues receive the message. The broker handles routing, delivery acknowledgment, and re-delivery of failed messages. Once a consumer acknowledges a message, the broker deletes it—messages are transient. RabbitMQ is the right fit when you need complex routing logic, when message ordering is not critical across consumers, or when you are building background job processing where each task should be handled exactly once. | **Complex Visual:** Design a diagram showing a message broker in action. The post office sorts them into mailboxes (queues) for the right recipients. Once a recipient picks up and reads a letter, the post office throws away the copy. |
| The second model is the event log, represented by Apache Kafka. Kafka is fundamentally different—it is not a smart router but a distributed, append-only log. Producers write events to a topic, which is a named, ordered log. Those events are persisted on disk and retained for a configurable duration—days, weeks, or indefinitely. Consumers read from the log at their own pace by tracking an offset—a position marker in the log. The critical difference from a broker: Kafka does not delete messages after consumption. Multiple consumer groups can read the same topic independently, each maintaining their own offset. A new consumer group can start from the beginning of the log and replay the entire event history. This makes Kafka ideal for event sourcing, audit trails, stream processing, and any architecture where you need to reconstruct state from historical events. Kafka also supports log compaction—a retention mode that keeps only the latest event for each key, making topics function as a durable key-value changelog. Kafka scales horizontally by dividing each topic into partitions—independent, ordered log segments. Each partition is consumed by exactly one consumer within a group, so adding partitions lets you parallelize processing. Kafka 4.0 runs exclusively on KRaft mode—an internal consensus protocol that manages cluster metadata, eliminating the previous dependency on ZooKeeper entirely. | **Complex Visual:** Design a diagram showing an event log. | When choosing between these two models, the decision comes down to your data lifecycle and consumption patterns. Use RabbitMQ when messages are commands or tasks—work items that should be processed once and discarded. Use Kafka when messages are events or facts—things that happened that you may need to replay, audit, or process with new consumers added after the fact. The delivery guarantee you configure also matters. At-most-once means a message may be lost but is never duplicated. At-least-once—the practical default for both systems—means a message is never lost but may be delivered twice, requiring your consumers to be idempotent. In Spring Boot, you interact with Kafka using `@KafkaListener` to consume messages from topics. When message processing fails, Spring Kafka provides `@RetryableTopic`—an annotation that automatically creates a chain of retry topics with increasing backoff delays. If all retries are exhausted, the message is routed to a Dead Letter Topic—a holding area for failed messages that can be inspected, debugged, and reprocessed manually. This pattern prevents a single "poison pill" message from blocking an entire partition. | |
| To summarize: asynchronous messaging decouples services temporally—producers and consumers do not need to be available at the same time. RabbitMQ is a message broker that routes and delivers messages, deleting them after acknowledgment—ideal for task distribution and complex routing. Kafka is an event log that persists events durably, allowing multiple consumers to read independently at their own pace—ideal for event-driven architectures, audit trails, and stream processing. In Spring Kafka, `@RetryableTopic` and Dead Letter Topics provide production-grade error handling that prevents failed messages from blocking your pipeline. The choice between broker and log is an architectural decision that depends on whether your data is ephemeral work or permanent record. Thanks for watching, and I'll see you in the next video. | |
