# Module 13: Understand Microservices Architecture Principles

## Video 1: When and Why to Decompose into Microservices

| Script (one row per slide) | Guidance for Complex Visuals |
| :--- | :--- |
| At some point in a growing engineering organization, a single application becomes a bottleneck—not because the code is bad, but because the teams working on it cannot move independently. A change to the checkout flow requires coordinating with the team that owns inventory, which shares a deployment pipeline with the team that owns user profiles. One failing component takes down everything. That organizational bottleneck is the real problem microservices solve. In this lesson, we are going to build a clear mental model for when a microservices architecture is worth the complexity—and, just as importantly, when it is not. | |
| A monolith is a single deployable unit where all domain logic—user management, ordering, payments, notifications—lives in one codebase and runs in one process. Monoliths get a bad reputation, but they have genuine strengths: simple deployment, straightforward debugging, easy local development, and no network latency between components because everything runs in-process. For a small team shipping a new product, a well-structured monolith is almost always the right starting point. The problems emerge at organizational scale. When multiple teams share a single codebase, merge conflicts multiply. A memory leak in the notification module crashes the entire application, including checkout. Scaling is all-or-nothing—you cannot independently scale the search component, which is CPU-intensive, separately from the order component, which is I/O-intensive. These are the forces that push teams toward decomposition. | **Complex Visual:** Design a single large box labeled "Monolith" containing four smaller sections stacked inside it, each labeled with a domain name: "Users," "Orders," "Payments," "Notifications." All four sections share the same border, indicating they are tightly packed together. Below the box, show a single deployment arrow pointing to a single server icon. To the right of the box, show a small crack or explosion icon in the "Notifications" section, with red color spreading to all other sections — indicating that one broken part affects everything. Note for designers: think of this like a single shipping container. If one item inside breaks and leaks, it damages everything else packed in the same container. |
| In a microservices architecture, each domain capability becomes its own independently deployable service with its own codebase, its own data store, and its own deployment pipeline. The Order Service does not share a database with the User Service—which means you lose cross-service SQL joins entirely. If the Order Service needs a customer's name, it calls the User Service's API or maintains its own denormalized copy of that data. Data duplication across service boundaries is not a bug—it is a deliberate trade-off for independence. Each team owns a complete vertical slice: from API endpoint to data persistence. This independence enables teams to deploy at their own pace, scale individual services based on their specific resource demands, and contain failures within service boundaries. But this independence comes with a cost. Every interaction that was a simple in-process method call in the monolith is now a network call—subject to latency, failure, and serialization overhead. These inter-service calls come in two forms: synchronous communication, where one service calls another via REST and waits for a response, and asynchronous communication, where a service publishes an event to a message broker and moves on without waiting. Synchronous is simpler but creates temporal coupling. Asynchronous decouples services in time but introduces eventual consistency—a model where different services may briefly see different versions of the truth. You now need service discovery to locate instances, distributed tracing to debug across service boundaries, and resilience patterns to handle the reality that any network call can fail. Microservices do not eliminate complexity—they redistribute it from the codebase to the infrastructure. | **Complex Visual:** Design four separate, evenly spaced boxes, each labeled with its domain: "Users," "Orders," "Payments," "Notifications." Each box has its own small database cylinder icon below it, and its own deployment arrow pointing to its own server icon. Between the boxes, draw thin dashed lines connecting them — representing network calls. Show the same crack or explosion icon in the "Notifications" box, but this time the red color stays contained within that single box — the other three remain unaffected. Note for designers: think of this like four separate shipping containers. If something breaks in one container, the others are completely isolated and safe. |
| The most common mistake teams make is decomposing too early or along the wrong boundaries. A microservice boundary should follow a bounded context—a domain-driven design concept where each service encapsulates a complete, self-contained business capability with its own data, its own rules, and its own language. The Order Service owns everything about orders: creation, status tracking, cancellation. It does not reach into the User Service's database to check customer details—it asks the User Service via an API call. If you find that two services constantly need to call each other to complete basic operations, your boundaries are wrong. A good litmus test: can a single team own, develop, deploy, and operate this service independently? If the answer is no, you have not found a real service boundary—you have split a monolith into a distributed monolith, which gives you all the operational overhead of microservices with none of the benefits. | |
| The decision of monolith versus microservices should be driven by organizational reality, not technical fashion. If you have a small team—fewer than ten engineers—a well-structured monolith with clear internal module boundaries will almost always move faster, cost less, and produce fewer production incidents than a premature microservices architecture. Microservices earn their complexity when you have multiple autonomous teams that need to ship independently, when different components have fundamentally different scaling requirements, and when fault isolation between domains is a genuine operational necessity. Start with a monolith, identify the pain points, and extract services along the boundaries that actually need independence. That pragmatic, need-driven decomposition produces far better architectures than adopting microservices on day one because it sounds modern.
