## Video 1: Standardizing Errors with RFC 9457

| If you want to gauge the engineering maturity of a team, look at how their APIs handle errors. A well-designed happy path is table stakes—every developer can build an endpoint that works when everything goes right. What separates production-grade APIs from prototypes is what happens when things go wrong. Does the client get a clear, structured error response that explains exactly what happened? Or does it get a cryptic 500 status code with an empty body—or worse, a raw framework stack trace? In this lesson, we are going to standardize error handling once and for all. | |
| The most common failure mode across microservice architectures is inconsistent error formats. One service returns a JSON object with an `error_message` field. Another uses `details`. A third nests a `status_code` inside a `meta` object, and a fourth returns raw HTML. The impact compounds as your system grows. Every frontend engineer consuming these APIs has to write custom parsing logic for each backend service, and that parsing breaks the moment someone on the backend changes the error shape without warning. For platform teams managing dozens of microservices, this inconsistency becomes a significant operational tax that slows down every team and every integration. | **Complex Visual:** Design a diagram with one box on the left labeled "Frontend App" and three boxes on the right labeled "Service A," "Service B," and "Service C." Service B's card has "details" and "timestamp." Service C's card has a nested structure with "meta > status_code." Inside the Frontend box, show a confused-face icon or a tangled mess of lines to represent the parsing headache. The key message: three services, three completely different error shapes, one frustrated frontend team. Note for designers: the field names on each card (like "error_message" and "status_code") should be displayed as plain text labels—like entries on a form. The point is that each card looks completely different from the others. Use visually distinct card styles (different colors, layouts, or fonts) for each service to emphasize the inconsistency. |
| The industry solved this with a standard: RFC 9457, Problem Details for HTTP APIs. You may also see it referenced by its original number, RFC 7807—the content is identical, but 9457 is the current Internet Standard, published in 2023. It defines a consistent JSON structure with five standard fields. `type` is a URI that categorizes the kind of error. `title` is a short, human-readable summary. `status` is the HTTP status code. `detail` is a specific explanation of what went wrong in this particular request. And `instance` is a URI identifying this specific occurrence for debugging. The power of a standard is interoperability: any client, API gateway, or monitoring tool that understands Problem Details can parse errors from any of your services identically—no custom logic required. | **Complex Visual:** Show a single clean card or JSON-shaped box with five clearly labeled rows, one for each field. Row 1: `type` — with an example value like "https://api.example.com/errors/order-not-found". Row 2: `title` — "Order Not Found." Row 3: `status` — "404." Row 4: `detail` — "No order exists with ID 987." Row 5: `instance` — "/orders/987". Use a clean, structured layout with each field name on the left in bold and the example value on the right. Add a small badge or banner at the top that says "RFC 9457 Standard Format." No code syntax—just a clean structured card. |
| Spring Framework provides native support for this standard through the `ProblemDetail` class, and the mechanism that ties it all together is `@RestControllerAdvice`—which combines `@ControllerAdvice` with `@ResponseBody`, ensuring all error responses are automatically serialized as JSON. A class annotated with `@RestControllerAdvice` acts as a centralized exception handler for your entire application. You define methods annotated with `@ExceptionHandler`, each targeting a specific exception type. When any controller throws that exception—say, an `OrderNotFoundException`—the advice intercepts it before the response is sent and translates it into a properly formatted Problem Details JSON response with the correct HTTP status code. This centralization is key. Without it, every controller method would need its own try-catch blocks, error formatting, and status code mapping. With `@RestControllerAdvice`, your controllers stay focused purely on business logic—they throw meaningful domain exceptions, and a single layer handles the HTTP translation. | |
| Two additional concerns are worth highlighting. First, validation errors. When a client sends a request that fails Jakarta Bean Validation—a missing field, an invalid email format—your `@ControllerAdvice` should catch the `MethodArgumentNotValidException` and return a Problem Details response that includes the specific field-level errors. This gives the client actionable information to fix the request rather than a vague rejection. Second, be deliberate about what you expose in error responses. Stack traces, internal class names, database column names—none of these should ever appear in a production error payload. A well-crafted error response tells the client exactly what went wrong and nothing about how your system is built. Security-sensitive information in error responses is one of the most common and most avoidable API vulnerabilities. | |
| A common temptation is to inject observability concerns directly into your error handlers—things like correlation IDs or distributed trace identifiers. Resist this. Error handling and observability are separate concerns. Trace propagation belongs in infrastructure-level middleware or dedicated tools like OpenTelemetry, not in your application's exception handlers. Mixing them creates tight coupling between your API error format and your monitoring stack, making both harder to change independently. Keep your error handlers focused on one job: producing clean, standards-compliant error responses. Thanks for watching, and I'll see you in the next video. | |
