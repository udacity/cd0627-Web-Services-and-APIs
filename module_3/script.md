## Video 1: How Spring Boot Handles HTTP Requests

| Building a REST API that follows clean design principles is one thing. Actually implementing it in code requires a framework that handles the heavy lifting—routing requests, converting data formats, managing the HTTP lifecycle. For the Java ecosystem, that framework is Spring Boot. In this lesson, we will look at how Spring Boot maps an incoming HTTP request to a specific piece of your code, how it converts between JSON and Java objects, and how it gives you a modern, declarative way to call other services. | |
| When an HTTP request hits your Spring Boot application, it passes through a well-defined pipeline. At the center sits the DispatcherServlet—Spring's front controller that receives every incoming request. It consults a handler mapping registry to determine which controller method should handle the request, matching on URL pattern and HTTP method. For example, a GET request to `/products/42` gets routed to a method annotated with `@GetMapping("/products/{id}")`. Once the right method is found, Spring deserializes the request body—if there is one—into a Java object, and passes in any path variables or query parameters as method arguments. Your controller class is annotated with `@RestController`—a convenience annotation that combines `@Controller` with `@ResponseBody`, telling Spring that every method's return value should be serialized directly as the response body rather than interpreted as a view template name. After your controller method returns a result, Spring passes it through an HttpMessageConverter, which serializes the Java object back into JSON for the response body. Understanding this pipeline matters because when something breaks—a 400 Bad Request, a serialization failure—knowing exactly where in this chain the failure occurred is what separates fast debugging from hours of guesswork. | **Complex Visual:** Design a horizontal flow diagram showing the journey of one request, left to right. | Now let us talk about making outbound HTTP calls—when your service needs to call another service. Historically, Java developers used `RestTemplate`, which required verbose, imperative code for every single call: manually building URLs, setting headers, handling errors, and deserializing responses. Spring Boot offers a far cleaner modern approach: the `@HttpExchange` declarative client. You define a Java interface, annotate its methods with `@GetExchange`, `@PostExchange`, or similar annotations, and Spring generates the implementation at runtime. You declare *what* the HTTP call looks like; the framework handles *how* it is executed. It is the same interface-driven philosophy that makes Spring Data repositories so productive—you write the contract, Spring writes the boilerplate. | **Complex Visual:** Design a before-and-after split panel. | Every time Spring converts a Java object to JSON or parses incoming JSON into a Java object, it relies on a serialization library. Spring Boot 4 ships with Jackson 3, which brings a major breaking change you need to know upfront: the package namespace has moved from `com.fasterxml.jackson` to `tools.jackson`. Knowing this saves you hours of compilation errors when upgrading legacy code. On the configuration side, Spring Boot defaults to ignoring unknown JSON properties, and you should keep it that way. If you configure Jackson to fail on unknown properties, your API becomes brittle—a frontend team adding a single harmless telemetry field to a JSON payload will instantly crash your backend. Be strict about what you send, but forgiving about what you receive. Where you should be explicit with your ObjectMapper is on output: formatting dates consistently and excluding null fields from responses. These configurations turn your serialization layer into a predictable, forward-compatible contract. | |
| One thing we are deliberately skipping in this course is content negotiation—the process of serving different response formats like XML or HTML based on the client's Accept header. Modern enterprise APIs communicate almost exclusively in JSON. Two concepts worth previewing here: first, `ResponseEntity`, which gives you fine-grained control over the HTTP status code and headers of your response; and second, API versioning using Spring Boot 4's native `version` attribute on `@GetMapping` and `@RequestMapping`, which lets you serve multiple API versions from a single codebase cleanly. By focusing on `@HttpExchange` for clean service communication, strict Jackson 3 configuration for robust serialization, and these modern versioning primitives, you are building with the tools that matter for production systems today.
