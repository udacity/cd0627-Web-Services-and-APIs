## Video 1: Protecting Services from Cascading Failures

| In a monolith, when one component fails, the whole application goes down—but at least the failure is obvious. In a microservices architecture, failures are far more insidious. The Payment Service slows down, so the Order Service threads start piling up waiting for responses. The Order Service stops responding, so the API Gateway threads back up. Within minutes, a single slow dependency has cascaded across your entire system, and every service is unresponsive. This is the cascading failure problem, and it is the most common cause of full-system outages in distributed architectures. In this lesson, we are going to understand the key resilience patterns that protect against it: circuit breaker, retry with exponential backoff, bulkhead—and the foundational pattern that makes them all work. | |
| The circuit breaker pattern is modeled after an electrical circuit breaker—a safety mechanism that trips and stops current flow when it detects a dangerous condition. In software, a circuit breaker monitors calls from one service to another and tracks the failure rate over a sliding window. It operates as a state machine with three states. In the Closed state—the normal operating mode—all requests flow through to the downstream service, and the circuit breaker silently monitors success and failure rates. If the failure rate exceeds a configured threshold—say, fifty percent of the last twenty calls fail—the circuit trips to the Open state. In the Open state, no requests reach the downstream service. Every call is immediately rejected with a fallback response, giving the struggling service time to recover. After a configured wait period, the circuit moves to Half-Open. It allows a small number of test calls through to probe whether the downstream service has recovered. If those test calls succeed, the circuit closes and normal traffic resumes. If they fail, the circuit reopens and the wait period restarts. In the Spring ecosystem, you implement this with Resilience4j, using the `@CircuitBreaker` annotation on methods that call external services. | **Complex Visual:** Design a horizontal state machine diagram with three rounded boxes in a row. | The second pattern is retry with exponential backoff and jitter. When a network call fails, the instinct is to retry immediately. But if the downstream service is overwhelmed, immediate retries from hundreds of clients create a thundering herd—a burst of synchronized traffic that makes the problem worse. Exponential backoff solves this by increasing the wait time between each retry attempt. The first retry waits one second. The second waits two seconds. The third waits four seconds. This progressively gives the struggling service more breathing room. Jitter adds randomness to each delay—instead of exactly four seconds, one client waits 3.2 seconds and another waits 4.7 seconds. This desynchronizes the retry waves across all clients, spreading the load over time rather than concentrating it in spikes. In Resilience4j, you configure this with the `@Retry` annotation and an `IntervalFunction` that combines exponential backoff with random jitter. A critical design decision: retries should only be applied to idempotent operations. Retrying a payment POST without an idempotency key risks charging a customer twice. | **Complex Visual:** Design a two-panel visual. Left panel, labeled "Without Backoff (Thundering Herd)": show five client icons on the left, each sending arrows simultaneously toward a single server icon on the right. The server is overwhelmed — show a red warning icon or explosion symbol next to it. All arrows arrive at the same time. Right panel, labeled "With Exponential Backoff + Jitter": show the same five client icons, but their arrows are staggered — each arrives at a different time, with increasing spacing. The first arrow is close to the start, each subsequent arrow is further apart, and they are slightly offset from each other (not perfectly evenly spaced — that is the jitter). The server icon looks healthy with a green checkmark. The key message: spread the load over time instead of slamming the server all at once. Note for designers: think of it like cars merging onto a highway — if they all try to merge at once, there is a traffic jam. If they stagger their entry with gaps between them, traffic flows smoothly. |
| The third pattern is the bulkhead. Named after the watertight compartments in ship design, a bulkhead limits the number of concurrent calls a service can make to any single dependency. Without one, a slow Payment Service can consume all of your Order Service's threads—leaving none available for the perfectly healthy Inventory or User Service. Resilience4j provides two implementations: a `SemaphoreBulkhead`, which limits concurrent calls using a permit counter, and a `ThreadPoolBulkhead`, which isolates calls to a dedicated thread pool. If all permits for the Payment Service are in use, new calls to that dependency are rejected—but every other dependency continues unaffected. You configure this with the `@Bulkhead` annotation. The pragmatic default is `SemaphoreBulkhead`—lightweight and compatible with Virtual Threads. | **Complex Visual:** Design a ship cross-section viewed from above (a top-down view of a ship hull). | These three patterns work together, but none of them helps if your outgoing calls can hang indefinitely. Timeouts are the foundation—a hard upper bound on how long any call is allowed to take. Without a timeout, a slow dependency holds your thread forever, and the circuit breaker never sees a failure to count. In Resilience4j, you configure this with a `TimeLimiter`. With timeouts in place, the circuit breaker stops calling a failing service when the failure rate is too high. Retry with backoff handles transient failures—brief network blips or temporary restarts—by spacing out attempts. And the bulkhead ensures that retries for one dependency cannot starve resources from others. In production, you stack all four: the timeout bounds each call, the bulkhead limits concurrency, the circuit breaker monitors failure rates, and retries handle transient errors. Resilience4j makes this composable—each pattern is a separate decorator, and you control the order in which they apply. Apply resilience patterns specifically to network boundaries—calls to external services, databases, and third-party APIs—where failure is not a possibility, it is an inevitability.
