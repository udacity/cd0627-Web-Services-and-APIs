# Module 12: Understand GraphQL Fundamentals

## Video 1: GraphQL's Schema-and-Resolver Model vs REST

| Think about the last time you built a mobile screen that needed data from three different REST endpoints. You made three sequential network calls, waited for all three to return, threw away half the fields you received, and then stitched the results together on the client side. That pattern—multiple round trips to assemble one screen, known as under-fetching—combined with over-fetched data and client-side assembly—is the core problem GraphQL was designed to solve. In this lesson, we are going to understand GraphQL's fundamentally different approach to API design: a schema-and-resolver model where the client decides exactly what data it needs, and the server delivers it in a single response. | |
| REST APIs are resource-oriented—you define a fixed endpoint for each resource, and every client that calls that endpoint gets the same response shape. That design works well when you have one or two clients with similar data needs. But in practice, a mobile app, a web dashboard, and a third-party integration all need different slices of the same data. The mobile client only needs a user's name and avatar. The dashboard needs the user's name, email, role, and last login timestamp. With REST, you have two options: return everything and let clients ignore what they do not need—that is over-fetching—or create separate endpoints for each client's specific needs, which fragments your API and increases maintenance burden. GraphQL takes a different approach entirely. Instead of the server defining what data gets returned, the client sends a query that specifies exactly which fields it wants, and the server returns precisely that shape—nothing more, nothing less. One endpoint, one round trip, zero wasted data. | **Complex Visual:** Design a two-panel comparison, side by side. Left panel, labeled "REST": show three stacked arrows going from a phone icon to three separate boxes labeled "Endpoint A," "Endpoint B," and "Endpoint C." Each box sends back an arrow carrying a card with 8-10 small square icons on it, but only 2-3 squares on each card are highlighted (the rest are grayed out), representing over-fetched data the client ignores. Right panel, labeled "GraphQL": show the same phone icon sending a single arrow to a single box labeled "GraphQL Endpoint." The box sends back one arrow carrying a card with exactly 3 highlighted squares on it—no grayed-out squares, no waste. The key contrast: three round trips with waste vs. one round trip with precision. Note for designers: the squares on the cards represent pieces of data (like fields on a form). Highlighted squares are data the client actually uses. Grayed-out squares are data the client received but threw away. |
| The foundation of every GraphQL API is its schema, written in the GraphQL Schema Definition Language. The schema is a strongly typed contract that defines every piece of data your API can serve and every operation clients can perform. There are two core operation types. A `Query` is a read operation—the GraphQL equivalent of a GET request. A `Mutation` is a write operation—the equivalent of POST, PUT, or DELETE. The schema defines the shape of these operations explicitly: what arguments they accept and what types they return. On the server side, every field in the schema is backed by a resolver—a function responsible for fetching or computing the data for that specific field. In Spring for GraphQL, resolvers are defined using `@QueryMapping` for top-level queries and `@SchemaMapping` for nested fields on specific types. The schema is the contract; resolvers are the implementation. This separation is what makes GraphQL APIs introspectable—clients can query the schema itself to discover available operations and types without any external documentation. | |
| There is, however, a critical performance trap that catches nearly every team the first time they build a GraphQL API: the N+1 problem. Imagine a query that fetches a list of ten orders, and for each order, resolves the associated customer. A naive implementation executes one query to fetch the ten orders, then ten individual queries—one per order—to fetch each customer. That is eleven database calls for what should be two. At scale, this pattern destroys performance. The standard solution in Spring for GraphQL is `@BatchMapping`. Instead of resolving one customer at a time, a method annotated with `@BatchMapping` receives the entire batch of parent objects—all ten orders—at once, letting you fetch all associated customers in a single database call. It is the difference between ten individual SELECT statements and one efficient IN clause. Understanding and applying batch loading is not optional—it is the minimum bar for a production GraphQL API. | **Complex Visual:** Design a two-panel visual. | GraphQL is not a replacement for REST—it is a complement. REST remains the better fit when you have well-defined, stable resource models consumed by a small number of clients with similar data needs. Its simplicity, mature caching infrastructure, and universal tooling make it the pragmatic default for most backend services. GraphQL becomes the stronger choice when you have multiple client types—mobile, web, third-party—each with different data requirements, or when your frontend teams are bottlenecked by having to request backend endpoint changes for every new screen they build. The decision should be driven by your actual client diversity and data access patterns, not by trend adoption. One important security note: GraphQL's introspection feature—which allows clients to explore your entire schema—should be disabled in production environments to prevent exposing your API's internal structure to potential attackers.
